## 1. 通用约定

### 1.1 Base URL

- 开发环境：`http://localhost:8080/api`（前端经 Vite 代理 `/api` 转发）
- 生产环境：`/api`（Nginx 反向代理到后端，前后端同域）

### 1.2 认证

- 登录/注册成功后返回 `token`；
- 除注册、登录、发送验证码、找回密码外，**其余接口**请求头携带：

```http
Authorization: Bearer <token>
```

- Token 过期或缺失：返回 `401`，前端跳转登录页。

### 1.3 统一响应格式

所有接口返回统一 JSON 结构，`code` 与 HTTP 状态码一致：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

失败示例：

```json
{
  "code": 409,
  "message": "用户名已存在",
  "data": null
}
```

### 1.4 错误码

| code | 含义 | 前端处理 |
| --- | --- | --- |
| 200 | 成功 | 正常解析 data |
| 400 | 参数错误/缺失/格式不对 | 提示 message |
| 401 | 未登录或登录过期 | 跳转登录页 |
| 403 | 无权限（如修改默认笔记本） | 提示 message |
| 404 | 资源不存在 | 提示 message |
| 409 | 业务冲突（用户名/邮箱/笔记本/标签重名等） | 提示 message |
| 500 | 服务器内部错误 | 统一提示"系统繁忙" |

> 数据隔离约定：访问**不属于当前用户**的数据统一返回 `404`（不区分"不存在"和"无权限"，避免泄露他人数据是否存在）。

### 1.5 分页格式

- 请求参数：`page`（从 1 开始，默认 1）、`pageSize`（默认 20，最大 50）；
- 响应 data：

```json
{
  "total": 56,
  "page": 1,
  "pageSize": 20,
  "records": []
}
```

### 1.6 时间格式

- 接口返回的 `LocalDateTime` 字段为 **ISO-8601** 格式：`yyyy-MM-dd'T'HH:mm:ss`（如 `2026-08-12T14:30:00`），无时区后缀；
- 前端展示时用 `.replace('T', ' ')` 转换为 `yyyy-MM-dd HH:mm:ss`（列表页再去掉秒）；
- 日期参数：`yyyy-MM-dd`（如 `2026-08-12`，`createdDate` 用）；
- 月份参数：`yyyy-MM`（如 `2026-08`，日历 `month` 用）；
- 统一使用北京时间（Asia/Shanghai，服务器本地时区）。

### 1.7 保存并发约定

- 自动保存即调用"更新笔记"接口，多端同时编辑**以最后保存为准**（Last-Write-Wins），后端不做版本冲突检测（P1 可选）。

## 3. 用户模块

### 3.1 注册

`POST /api/auth/register`

请求：

```json
{
  "username": "zhangsan",
  "password": "123456",
  "email": "zhangsan@example.com",
  "code": "123456"
}
```

校验：用户名 3~20 位（字母/数字/下划线）；密码 6~20 位；邮箱格式合法；验证码为 6 位数字且须与邮箱匹配、未过期。

成功响应（注册后自动登录，直接返回 token）：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "token": "a1b2c3d4...",
    "user": {
      "id": 1,
      "username": "zhangsan",
      "nickname": null,
      "avatar": null
    }
  }
}
```

错误：`409` 用户名已存在 / 邮箱已被注册；`400` 验证码错误或已过期 / 参数不合法。

> 后端在注册成功后自动创建该用户的"默认笔记本"。

### 3.2 发送邮箱验证码（注册）

`POST /api/auth/send-code`

请求：

```json
{
  "email": "zhangsan@example.com"
}
```

成功响应：`data: null`（验证码发送至该邮箱，6 位数字，5 分钟内有效）。

错误：

- `400` 邮箱格式不合法 / 发送过于频繁（同一邮箱 60 秒内只允许发送一次）；
- `409` 该邮箱已被注册。

> 验证码由后端服务端邮箱（QQ 邮箱 SMTP）发送；验证码内存存储，服务重启后失效。

### 3.3 登录

`POST /api/auth/login`

请求：

```json
{
  "username": "zhangsan",
  "password": "123456"
}
```

成功响应：同注册返回结构（`token` + `user`）。

错误：`401` 用户名或密码错误。

### 3.4 登出

`POST /api/auth/logout`

请求：无 Body。

成功响应：`data: null`。

> JWT 为无状态认证：登出由前端清除本地 token 完成；如需服务端强制失效（如改密码踢下线），可引入 Redis 黑名单（P1）。

### 3.5 当前用户信息

`GET /api/auth/me`

说明：前端刷新页面时用 token 恢复登录态；未登录返回 `401`。

成功响应：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "id": 1,
    "username": "zhangsan",
    "nickname": null,
    "avatar": null
  }
}
```

### 3.6 找回密码

**第一步：发送验证码**

`POST /api/auth/password/reset-code`

请求：`{ "email": "zhangsan@example.com" }`

成功响应：`data: null`。

错误：`400` 邮箱格式不合法 / 发送频繁；`404` 该邮箱未注册。

**第二步：重置密码**

`POST /api/auth/password/reset`

请求：

```json
{
  "email": "zhangsan@example.com",
  "code": "123456",
  "newPassword": "654321"
}
```

成功响应：`data: null`；错误：`400` 验证码错误或已过期 / 新密码不合法。

### 3.7 修改密码（登录后）

**第一步：发送验证码**

`POST /api/auth/password/change-code`

请求：无 Body（验证码发送至当前登录用户的邮箱）。

成功响应：`data: null`；错误：`401` 未登录 / 当前账号无邮箱。

**第二步：修改密码**

`POST /api/auth/password/change`

请求：

```json
{
  "code": "123456",
  "newPassword": "654321"
}
```

成功响应：`data: null`；错误：`400` 验证码错误或已过期 / 新密码不合法。

## 4. 图片模块

### 4.1 上传图片

`POST /api/images/upload`

请求：`multipart/form-data`，字段名 `file`。

成功响应：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "url": "/uploads/2026/08/14/xxxx.png"
  }
}
```

说明：

- 图片保存为服务器磁盘独立文件，正文 HTML 中只保存 `url`（相对路径，前端拼 `http://host` 前缀访问）；
- 上传即写入一条 `note_image`（此时 `note_id` 为空，属临时图片）；笔记创建/更新时后端解析正文 url 回填 `note_id` 绑定；
- 静态资源映射：`/uploads/**` → 磁盘 uploads 目录（已配置尾斜杠，保证路径正确拼接）；
- 错误：`400` 文件为空 / 类型或大小超限。

## 5. 笔记本模块

### 5.1 笔记本列表

`GET /api/notebooks`

成功响应：

```json
{
  "code": 200,
  "message": "success",
  "data": [
    {
      "id": 1,
      "name": "默认笔记本",
      "isDefault": true,
      "noteCount": 12,
      "createTime": "2026-08-12T10:00:00"
    },
    {
      "id": 2,
      "name": "工作",
      "isDefault": false,
      "noteCount": 5,
      "createTime": "2026-08-12T11:00:00"
    }
  ]
}
```

> `noteCount` 为笔记数（不含回收站），按创建时间倒序。

### 5.2 笔记本下的笔记列表

`GET /api/notebooks/{id}/notes`

查询参数：`page` 默认 1，`pageSize` 默认 30、最大 50。

说明：分页返回该笔记本下的正常笔记轻量信息（仅 `id`、`title`，置顶优先、按最后编辑时间倒序），供侧边栏逐页展开使用。

成功响应：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "total": 2,
    "page": 1,
    "pageSize": 30,
    "records": [
      { "id": 101, "title": "周会纪要" },
      { "id": 99, "title": "待办清单" }
    ]
  }
}
```

错误：`404` 笔记本不存在。

### 5.3 新建笔记本

`POST /api/notebooks`

请求：`{ "name": "学习" }`（1~50 字符）

成功响应：`data` 为笔记本对象（同列表项结构）。

错误：`409` 同名笔记本已存在。

### 5.4 重命名

`PUT /api/notebooks/{id}`

请求：`{ "name": "新名字" }`

成功响应：`data` 为更新后的笔记本对象。

错误：`400` 默认笔记本不可重命名；`409` 名称已存在；`404` 不存在。

### 5.5 删除笔记本

`DELETE /api/notebooks/{id}`

成功响应：`data: null`（其下所有笔记一并移入回收站，待提醒取消）。

错误：`400` 默认笔记本不可删除；`404` 不存在。

## 6. 笔记模块（含搜索、筛选、日历当天）

### 6.1 笔记列表 / 搜索 / 筛选

`GET /api/notes`

查询参数（全部可选）：

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| page | int | 页码，默认 1 |
| pageSize | int | 每页条数，默认 20，最大 50 |
| notebookId | int | 按笔记本筛选 |
| tagId | int | 按标签筛选 |
| keyword | string | 搜索关键词（匹配标题 + 正文纯文本） |
| createdDate | string | 按创建日期筛选，格式 `yyyy-MM-dd`（日历当天用） |

成功响应：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "total": 56,
    "page": 1,
    "pageSize": 20,
    "records": [
      {
        "id": 101,
        "title": "周会纪要",
        "contentPreview": "1. 完成数据库设计...",
        "pinned": 0,
        "notebookId": 2,
        "notebookName": "工作",
        "tags": [
          { "id": 5, "name": "会议" },
          { "id": 9, "name": "待办" }
        ],
        "createTime": "2026-08-12T09:00:00",
        "updateTime": "2026-08-12T14:30:00"
      }
    ]
  }
}
```

说明：

- 默认排序：**置顶优先，再按最后编辑时间倒序**（`pinned DESC, update_time DESC`）；
- `keyword` 存在时按 `title LIKE '%kw%' OR content_text LIKE '%kw%'` 检索（`content_text` 为正文剥离 HTML 后的纯文本列）；
- `contentPreview` 取正文剥壳纯文本前 100 字。

### 6.2 笔记详情

`GET /api/notes/{id}`

成功响应：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "id": 101,
    "title": "周会纪要",
    "content": "<p>完成数据库设计</p>",
    "pinned": 0,
    "notebookId": 2,
    "notebookName": "工作",
    "tags": [
      { "id": 5, "name": "会议" }
    ],
    "reminder": {
      "id": 31,
      "noteId": 101,
      "remindAt": "2026-08-13T14:30:00",
      "status": 0
    },
    "createTime": "2026-08-12T09:00:00",
    "updateTime": "2026-08-12T14:30:00"
  }
}
```

> `content` 为富文本 HTML；`reminder` 无"待提醒"时为 `null`（已提醒/已取消的不再返回）；`status`：0 待提醒 / 1 已提醒 / 2 已取消。

错误：`404` 笔记不存在。

### 6.3 新建笔记

`POST /api/notes`

请求：

```json
{
  "notebookId": 2,
  "title": "周会纪要",
  "content": "<p>周会纪要</p>",
  "tagIds": [5, 9]
}
```

参数说明：

- `notebookId` 可省略，默认放入"默认笔记本"；
- `title` 可省略，后端自动取正文纯文本前 50 字；
- `content` 为富文本 HTML（可省略）；
- `tagIds` 可省略或为空数组。

成功响应：`data` 为完整笔记对象（含 `id`，同详情结构）。

### 6.4 保存笔记（自动保存）

`PUT /api/notes/{id}`

请求：

```json
{
  "title": "周会纪要（更新）",
  "content": "<p>周会纪要</p><p>更新内容</p>",
  "tagIds": [5, 9, 12]
}
```

说明：

## 12. AI 索引与检索模块

> **本章说明**：第 12～14 章覆盖索引管理、运行状态与 AI 编辑；AI 问答、会话、反馈与回归评估在第 15、16 章。

### 12.0 时间格式例外

本章的 `lastUpdatedAt` / `createdAt` 是 `Instant`，序列化为 **UTC ISO-8601 且带 `Z` 后缀**，例如 `2026-09-18T11:40:35.503096700Z`，**与 1.6 节的 `LocalDateTime` 约定不同**。

前端直接交给 `new Date(v).toLocaleString('zh-CN')` 即可正确转成北京时间；**不要**对它做 `.replace('T', ' ')`，否则显示的是 UTC 时间，会差 8 小时。

### 12.1 索引健康状态

`GET /api/ai/notes/index/status`

成功响应：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "noteCount": 41,
    "indexedNoteCount": 41,
    "chunkCount": 210,
    "missingNoteCount": 0,
    "staleChunkCount": 0,
    "storeFileExists": true,
    "storeFileBytes": 3090054,
    "lastUpdatedAt": "2026-09-19T02:21:30.284537900Z",
    "state": "HEALTHY",
    "storeType": "simple",
    "indexType": null
  }
}
```

`state` 取值：

| state | 含义 |
| --- | --- |
| `HEALTHY` | 正常笔记均已建立索引，且无残留片段 |
| `EMPTY` | 当前没有需要建立索引的笔记 |
| `NEEDS_REBUILD` | 有笔记缺失索引，或存在已删除笔记的残留片段 |
| `ERROR` | 索引文件无法读取（JSON 损坏等），需执行重建 |

`storeType` / `indexType` 描述当前生效的向量存储，用于让对比报告自描述：

| 字段 | 取值 |
| --- | --- |
| `storeType` | `simple`（进程内 SimpleVectorStore，默认）或 `pgvector` |
| `indexType` | `pgvector` 时为 `NONE` / `IVFFLAT` / `HNSW`；`simple` 时为 `null`（它不是索引型存储） |

> **向量存储是可切换的。** `NOTEPAD_VECTOR_STORE_TYPE=simple|pgvector` 控制，默认 `simple`。
> 切到 pgvector 需要额外跑一个带 pgvector 扩展的 PostgreSQL 实例，
> 以及 `NOTEPAD_PGVECTOR_URL` / `NOTEPAD_PGVECTOR_USERNAME` / `NOTEPAD_PGVECTOR_PASSWORD`。
> 两种存储下的接口、快照格式、备份恢复流程完全一致，互相切换只需重启。
> 迁移方式就是「在一种模式下备份 → 切到另一种模式 → 恢复同一份快照」。
> 实测对比结论见 [07-pgvector迁移对比报告](./07-pgvector迁移对比报告.md)。
>
> `pgvector` 模式下 `storeFileExists` 恒为 `true`、`storeFileBytes` 为 `0` —— 它的持久化载体是数据库而不是本地文件。

### 12.2 建立索引

`POST /api/ai/notes/{noteId}/index` — 为单篇笔记建立索引。

```json
{ "noteId": 61, "title": "day5", "chunkCount": 4 }
```

`POST /api/ai/notes/index-all` — 为当前用户全部正常笔记建立索引，与重建接口共用响应：

```json
{ "noteCount": 41, "chunkCount": 210 }
```

一篇笔记会按 token 切成多个片段，`chunkCount` 是片段数而非笔记数。`404` 笔记不存在或不属于当前用户。

### 12.3 重建索引

`POST /api/ai/notes/index/rebuild`

只清理并重建**当前用户**的向量，不影响同一文件里其他用户的数据。响应同 12.2 的批量格式。

> 重建会重新调用百炼 Embedding，消耗额度。前端在触发前必须二次确认。

### 12.4 向量检索

`POST /api/ai/notes/search`

请求：

```json
{ "question": "Stream 流的特点" }
```

响应 `data` 为片段数组，按相关度降序：

```json
[
  { "noteId": 53, "title": "day1", "content": "(arr) 零散的数据就直接 stream.", "score": 0.5564 }
]
```

`content` 是切分后的**片段正文**，不含笔记标题（标题只有索引时的原始文档才带）；`title` 单独返回。只调用 Embedding 做检索，不调用回答模型。结果已按 `userId` 过滤，不会跨用户。

### 12.5 备份列表

`GET /api/ai/notes/index/backups`

```json
[
  {
    "fileName": "simple-vector-store-20260918-194027-1339ef32.json",
    "fileBytes": 3090024,
    "createdAt": "2026-09-18T11:40:21.679144100Z",
    "reason": "manual"
  }
]
```

`reason` 取值 `manual`（手动创建）或 `pre-restore`（恢复前自动留档）。列表按创建时间倒序，只读文件元数据，**不校验内容**。

### 12.6 创建备份

`POST /api/ai/notes/index/backups`

把当前索引完整复制一份到 `backend/data/backups/`，命名为 `simple-vector-store-{yyyyMMdd-HHmmss}-{8位随机}.json`。响应为单个条目，字段同 12.5。

- 默认保留最近 10 份（`notepad.ai.backup-retention`），超出后按最旧优先清理。
- 创建过程**不影响正在使用的索引**。
- 索引文件不存在时返回 `400`，不会伪造空备份。

### 12.7 校验备份

`GET /api/ai/notes/index/backups/{fileName}/verify`

```json
{ "fileName": "...", "valid": true, "entryCount": 210, "userCount": 1, "issueMessage": null }
```

**无任何副作用**，供前端在发起恢复前预检。校验项包括：JSON 可解析、每条片段的 `embedding` 恰好 1024 维、`documentId` 与 `metadata` 的 `userId`/`noteId` 自洽、`metadata.title` 非空。`valid` 为 false 时 `issueMessage` 说明首个失败原因。

### 12.8 从备份恢复

`POST /api/ai/notes/index/backups/{fileName}/restore`

```json
{
  "fileName": "simple-vector-store-20260918-194027-1339ef32.json",
  "restoredEntryCount": 210,
  "storeFileBytes": 3090024,
  "snapshotFileName": "simple-vector-store-20260918-194035-pre-restore-9e22268a.json",
  "status": { }
}
```

`status` 是恢复后重新读取的健康状态，结构同 12.1。

- 服务端在执行前会**自动把当前索引留档**一份（`reason=pre-restore`），其文件名通过 `snapshotFileName` 返回，可用于回退。
- 校验不通过返回 `400` 并给出具体原因，**此时磁盘和内存中的索引都未被改动**。
- 备份文件不存在或文件名不符规范返回 `404`；路径穿越返回 `400`。
- **恢复是全局操作**：一份文件承载全部用户的片段，恢复会把所有用户的索引一起回退到备份时间点。前端必须二次确认并在文案中说明这一点。

> ⚠️ 备份与恢复接口目前**没有权限门禁**，任何登录用户均可调用。这是已知取舍，缓解措施为严格的文件名校验、恢复前强制留档和带 `userId` 的审计日志。

## 13. AI 运行状态与统计

两个只读接口，用于排查限流、超时和上游故障，不修改任何状态。

### 13.1 并发许可状态

`GET /api/ai/concurrency/status`

```json
{ "activeCount": 0, "availableGlobalPermits": 4, "globalMax": 4, "perUserMax": 1 }
```

**静止时刻必须满足守恒律**：

```
activeCount + availableGlobalPermits == globalMax
```

因为 `tryAcquire` 只在拿到全局许可后才递增用户计数，超限回滚与 `Permit.close()` 也都是同时递减计数并释放全局许可，两者始终同增同减。任何一条请求路径漏掉 `Permit.close()`，这条等式立刻不成立，而且能区分是全局信号量泄漏还是单用户计数泄漏。

这是判断并发许可是否泄漏最直接的观测点。`globalMax` / `perUserMax` 来自 `notepad.ai.concurrency.*`。

### 13.2 请求统计

`GET /api/ai/metrics`

```json
{
  "rejectedStream": 0,
  "rejectedBlocking": 0,
  "rejectedQueue": 0,
  "timeout": 0,
  "retry": 0,
  "completed": 0,
  "failed": 0,
  "durationDistribution": { "<=1s": 0, "1s~3s": 0, "3s~10s": 0, "10s~30s": 0, "30s~60s": 0, ">60s": 0 }
}
```

| 字段 | 含义 |
| --- | --- |
| `rejectedStream` | 流式问答（`/api/ai/notes/ask/stream`）因并发上限被拒 |
| `rejectedBlocking` | 阻塞式问答（`/api/ai/chat`、`/api/ai/notes/ask`）因并发上限被拒 |
| `rejectedQueue` | 因 AI 线程池队列已满被拒 |
| `timeout` | 超时（SSE 通道超时或上游超时） |
| `retry` | 上游调用**确实发生的重试次数**（不是失败次数） |
| `completed` / `failed` | 成功完成 / 最终失败的问答数 |
| `durationDistribution` | 端到端耗时分桶，桶边界为 1s / 3s / 10s / 30s / 60s |

**三点必须知道的口径**：

1. **纯内存计数，服务重启归零。** 每个计数点同时都会打一条 `event=...` 结构化日志（如 `event=ai.stream.rejected`、`event=ai.request.rejected`、`event=ai.retry.observed`），需要跨重启的历史趋势时对日志聚合即可。
2. **`retry` 只统计确实又发起了一次尝试的情况。** Spring AI 的重试策略是 `RetryTemplate.builder().retryOn(TransientAiException.class)` —— **只重试 `TransientAiException`**。裸的连接失败（`ResourceAccessException`）不会被重试，只有被 `ResponseErrorHandler` 归类为瞬态的响应（HTTP 5xx 等）才会。
3. **不要把框架日志 `Retry error. Retry count: N` 当成重试次数。** 那是 `SpringAiRetryAutoConfiguration` 自己的 `RetryListener.onError` 打出的**失败序号**，每次失败尝试都会打。例如无效 API Key 返回 401 时只尝试 1 次、不发生重试，日志照样写 `Retry count: 1`。以 `retry` 字段或 `event=ai.retry.observed attempts= retries=` 为准。

> 每个请求的耗时同时也会出现在对应的结构化日志里：流式是 `event=ai.stream.completed` 的 `totalMs=`，检索是 `event=ai.retrieval.completed` 的 `durationMs=`。

## 14. AI 编辑笔记

流程固定为 **读取当前笔记 → AI 生成预览 → 用户确认 → 写回笔记 → 重新同步向量索引**。
**模型不直接写库**：预览接口只产出文本，写回必须由 apply 接口在客户端回传内容指纹、校验通过之后才发生。

### 14.1 四种能力

| capability | 输出 | 写回方式 |
| --- | --- | --- |
| `summarize` 摘要 | 摘要段落 | **插入正文开头**（原文保留） |
| `rewrite` 改写 | 改写后的正文 | **替换正文**（写回前自动存原文快照） |
| `continue` 续写 | 续写段落 | **追加到正文末尾** |
| `todos` 提取待办 | 待办列表 | **追加到正文末尾** |

模型输入是笔记的**纯文本**（`content_text`），不是 HTML。

### 14.2 流式生成预览

`POST /api/ai/notes/{noteId}/ai-edit/preview/stream`

请求：`{ "capability": "summarize" }`

SSE 事件顺序：

```
status {phase:"generating", requestId}
delta  {text}            × N
done   {requestId, contentHash, capability}
```

出错时发 `error {message, errorId}`；并发超限时额外带 `retryAfterSeconds` 与响应头 `Retry-After: 2`。

**`contentHash` 是生成预览时笔记正文的 SHA-256**，写回时必须原样回传。它挡的是「用户在生成预览的十几秒里顺手改了笔记，一确认就丢了」——这正是「模型不得直接覆盖用户内容」要防的场景。

> 该接口同样受 AI 并发限制，计入 `/api/ai/metrics`。

### 14.3 确认写回

`POST /api/ai/notes/{noteId}/ai-edit/apply`

```json
{ "capability": "rewrite", "text": "AI 生成的正文", "contentHash": "预览时拿到的指纹" }
```

成功返回：

```json
{ "revisionId": 12, "note": { } }
```

`note` 是写回后的完整笔记详情（结构同 `GET /api/notes/{id}`）。

- **内容指纹不匹配返回 `409`**「笔记在生成预览期间已被修改，请重新生成后再应用」，**绝不覆盖**
- 笔记不存在或不属于当前用户返回 `404`
- 写回前会自动把原文存入 `ai_note_revision` 表（每篇笔记保留最近 10 份），返回的 `revisionId` 可用于回退
- 写回走的是与 `PUT /api/notes/{id}` 相同的服务方法，**标签、图片绑定与向量重新同步都会照常执行**

> **转义约定**：AI 输出是纯文本，服务端在包成 `<p>` 之前会先做 HTML 转义。
> 正文最终由富文本编辑器渲染，不转义的话模型输出里的标签会变成可执行标记。

### 14.4 原文快照与回退

`GET /api/ai/notes/{noteId}/ai-edit/revisions`

```json
[ { "id": 12, "capability": "rewrite", "createTime": "2026-09-19T11:22:09", "restored": false, "restoreTime": null } ]
```

`POST /api/ai/notes/{noteId}/ai-edit/revisions/{revisionId}/restore`

把正文恢复到那次 AI 编辑之前，返回恢复后的笔记详情。**允许重复回退**（用户可能回退后又做了别的编辑，再想回到同一版本）。

## 15. AI 问答与会话

> 索引由向量库承载（默认进程内 `SimpleVectorStore`，可切 pgvector，见第 12 章）。笔记新增、编辑、移动、删除后由后端**异步同步**（写回类操作有 5 秒防抖），无需前端显式调用索引接口。
>
> 所有 AI 接口共用一套**并发限制**：全局上限 4、单用户上限 1。超出时返回可重试提示，HTTP 响应头带 `Retry-After: 2`（流式接口则在 SSE 的 error 事件里带 `retryAfterSeconds`）。

### 15.1 普通聊天（不检索笔记）

`POST /api/ai/chat`

```json
{ "message": "你好" }
```

返回 `data` 为字符串。**不检索笔记**，仅用于无需笔记依据的场景。

### 15.2 基于笔记阻塞问答

`POST /api/ai/notes/ask`

```json
{
  "question": "SQL 优化可以按照什么步骤排查？",
  "history": [
    { "role": "user", "content": "我之前问过什么？" },
    { "role": "assistant", "content": "你问过……" }
  ],
  "noteId": null,
  "notebookId": null
}
```

| 字段 | 说明 |
| --- | --- |
| `question` | 必填，最长 500 字 |
| `history` | 可选，最多 10 条，只用于理解追问中的指代，**不作为笔记事实来源** |
| `noteId` | 可选，限定为「当前笔记」范围 |
| `notebookId` | 可选，限定为「当前笔记本」范围 |

响应：

```json
{
  "answer": "根据你的笔记，SQL 优化可以按以下步骤排查……",
  "sources": [
    { "noteId": 61, "title": "day5", "content": "……片段原文……", "score": 0.71 }
  ]
}
```

`sources` 是本次回答**实际使用**的检索片段，供前端展示引用并跳转原笔记。回答严格依据检索到的笔记；检索不到时明确拒答。

### 15.3 基于笔记流式问答

`POST /api/ai/notes/ask/stream`，请求体同 15.2。

SSE 事件顺序：

```
status {phase:"retrieving", requestId}
status {phase:"generating", requestId}
delta  {text}                   × N
sources [ {noteId, title, content, score} ]
done   {requestId}
```

错误事件 `error {message, errorId, retryAfterSeconds?}`。

- 前端用 **fetch 而非 EventSource** 消费：EventSource 只支持 GET，而这里需要带 JSON 请求体与鉴权头
- 支持中途停止（abort）
- 单次生成超时 150 秒；SSE 通道超时 180 秒

### 15.6 保存会话

`PUT /api/ai/conversations/{clientId}`

```json
{
  "title": "SQL 优化",
  "messages": [ ]
}
```

`messages` 每条最多 5 个引用片段，整个会话最多 20 条消息。**整体覆盖**：以本次提交的消息为准。

`clientId` 与 `clientMessageId` 都是前端生成的、形如 `[A-Za-z0-9-]{1,64}` 的标识，用于在服务端去重与关联。

### 15.7 删除会话

`DELETE /api/ai/conversations/{clientId}`

**级联删除**该会话的消息与反馈。

### 15.8 提交 / 修改反馈

`PUT /api/ai/conversations/{clientId}/messages/{messageClientId}/feedback`

```json
{ "rating": "unhelpful", "reason": "incomplete", "comment": "没有覆盖索引失效的情况" }
```

| 字段 | 取值 |
| --- | --- |
| `rating` | `helpful` / `unhelpful` |
| `reason` | `unhelpful` 时必填：`irrelevant_sources` / `incomplete` / `inconsistent` / `wrong_scope` / `other` |
| `comment` | 可选，最长 500 字 |

返回：

```json

```

同一条消息重复提交会**覆盖**原有反馈（用于修改反馈）。`helpful` 会清空 `reason` 与 `comment`。

> 反馈保存的是**评价时的快照**（问题、回答、引用片段、检索范围），不受后续会话编辑影响。

### 15.9 删除反馈

`DELETE /api/ai/conversations/{clientId}/messages/{messageClientId}/feedback`

### 16.1 反馈统计

`GET /api/ai/feedback/statistics`

```json
{
  "totalCount": 12,
  "helpfulCount": 9,
  "unhelpfulCount": 3,
  "helpfulRate": 0.75,
  "convertedCaseCount": 1,
  "conversionRate": 0.3333333333333333,
  "reasonCounts": [
    { "reason": "incomplete", "count": 2, "rate": 0.6666666666666666 },
    { "reason": "irrelevant_sources", "count": 1, "rate": 0.3333333333333333 }
  ],
  "commonFailureQuestions": [
    {
      "question": "SQL 优化可以按照什么步骤排查？",
      "count": 2,
      "convertedCaseCount": 1,
      "lastFeedbackAt": "2026-09-19T11:20:00",
      "reasonCounts": [ { "reason": "incomplete", "count": 2, "rate": 1.0 } ],
      "evalStatus": "passed",
      "lastEvalAt": "2026-09-19T11:25:00",
      "evalFailureReason": null
    }
  ]
}
```

| 字段 | 说明 |
| --- | --- |
| `convertedCaseCount` | 该高频问题下已转成回归用例的**去重用例数** |
| `evalStatus` | 这些用例在**最近一次**回归报告里的状态：`passed` / `failed` / `not_run` |
| `lastEvalAt` | 最近一次回归的时间；`not_run` 时为 `null` |
| `evalFailureReason` | 仅 `failed` 时有值，与回归报告里的失败原因逐字一致 |

> `evalStatus` 把「用户反馈的问题」与「回归测试报告」关联起来：用户反馈过的问题现在修好没有，看这个字段即可。
> 只统计**真正出现在最近一次报告里**的用例 —— 被停用或从未跑过的不算「通过」，而是 `not_run`。

### 16.3 新建 / 修改 / 删除用例

- `POST /api/ai/evaluations/cases` —— 新建
- `PUT /api/ai/evaluations/cases/{caseId}` —— 修改
- `DELETE /api/ai/evaluations/cases/{caseId}` —— 删除

请求体（三个接口共用）：

```json
{
  "name": "SQL 优化排查步骤",
  "question": "SQL 优化可以按照什么步骤排查？",
  "scopeType": "all",
  "scopeId": null,
  "expectAnswer": true,
  "expectedNoteIds": [61],
  "matchMode": "any",
  "minScore": 0.45,
  "enabled": true
}
```

| 字段 | 说明 |
| --- | --- |
| `scopeType` | `all` / `notebook` / `note`；非 `all` 时必须给 `scopeId` |
| `expectAnswer` | `true` 应命中 / `false` 应拒答 |
| `expectedNoteIds` | 应命中时允许命中的笔记集合，最多 10 篇 |
| `matchMode` | `any` 命中其一即可 / `all` 必须全部命中 |
| `minScore` | 最低相关度，取值 0.30 ~ 1.00 |
| `enabled` | 停用的用例不参与运行 |

> **应命中的用例必须同时满足「命中预期集合」且「没有命中集合外的笔记」**，否则算失败 —— 这是为了防止「命中是命中了，但引用了不该引用的笔记」。

每个用户最多 100 个用例。

### 16.4 由反馈转为回归用例

`POST /api/ai/evaluations/cases/from-feedback/{conversationClientId}/{messageClientId}`

请求体同 16.3。要求该消息已被标记为 `unhelpful`，否则返回 `404`。

**幂等**：同一反馈重复调用会返回已转换出的那个用例，不会重复创建。转换成功后会把用例 ID 记回反馈行，用于防止重复转换。

### 16.5 运行回归 / 历史报告

`GET /api/ai/evaluations/runs` —— 历史报告列表（只保留最近 10 次）：

```json
[
  {
    "id": 49,
    "caseCount": 14,
    "passedCount": 14,
    "passRate": 1.0,
    "hitRate": 1.0,
    "rejectionAccuracy": 1.0,
    "wrongReferenceCount": 0,
    "averageDurationMs": 445,
    "createdAt": "2026-09-19T11:30:00"
  }
]
```

`POST /api/ai/evaluations/runs` —— 运行全部启用用例，返回完整报告（含逐用例明细）。

`GET /api/ai/evaluations/runs/{runId}` —— 查看某次报告明细。

**报告指标**：

| 字段 | 含义 |
| --- | --- |
| `passRate` | 整体通过率 |
| `hitRate` | Top-K 命中率（应命中的用例中命中的比例） |
| `rejectionAccuracy` | 正确拒答率（应拒答的用例中正确拒答的比例） |
| `wrongReferenceCount` | 命中了预期集合之外笔记的次数 |
| `averageDurationMs` | 平均检索耗时 |

逐用例明细 `results[]`：

```json
{
  "caseId": 15,
  "name": "反馈·回答不完整·SQL 优化……",
  "question": "SQL 优化可以按照什么步骤排查？",
  "expectAnswer": true,
  "expectedNoteIds": [61, 65],
  "matchedNoteIds": [61],
  "topScore": 0.6842,
  "wrongReferenceCount": 0,
  "durationMs": 412,
  "passed": true,
  "failureReason": null,
  "retrievalTraces": [ ],
  "sourceFeedback": {
    "feedbackId": 4,
    "reason": "incomplete",
    "comment": "没有覆盖索引失效的情况",
    "feedbackAt": "2026-09-19T11:20:00"
  }
}
```

- `retrievalTraces` 是每个子查询的候选轨迹（候选笔记、分数、是否入选），仅在失败时前端会展示，用于解释「为什么没命中」
- **`sourceFeedback` 只在由反馈转换来的用例上出现**，手工创建的用例为 `null`。它让回归报告可以直接追溯到用户当时的原始反馈

**回归只调用 Embedding 做检索，不调用回答模型**，所以 `averageDurationMs` 就是纯粹的检索耗时。

> 每次运行最多 30 个用例。**不要因为单个用例失败就调 `minScore` 或检索阈值** —— 先判断预期集合是否配全。

## 17. 前端联调约定

1. **axios 拦截器**：
   - 请求拦截：从 localStorage 取 token，自动加 `Authorization: Bearer <token>` 请求头；
   - 响应拦截：`status === 401` 时清除 localStorage 与 Pinia 登录态并跳转登录页；其他非 200 统一 `ElMessage.error(message)`。
2. **Token 存储**：登录/注册后存入 localStorage（key：`token`）。
3. **实时保存**：编辑器内容/标题变化即触发保存（串行队列，切走/卸载前强制落盘），调用 `PUT /api/notes/{id}`，成功后轻提示"已保存"；保存失败保留编辑内容并提示。
4. **图片上传**：wangEditor 配置 `customUpload` 调用 `POST /api/images/upload`，`base64LimitSize = 0` 禁用 base64。
5. **导出**：纯前端，Turndown 将正文 HTML 转 Markdown，本地 Blob 下载 `.md`，无后端接口。
6. **日历**：切换月份调用一次 `GET /api/calendar/marks?month=xxx` 获取标记日期；点击日期调用 `GET /api/notes?createdDate=xxx`。
7. **提醒状态**：进入笔记详情时从 `reminder` 字段读取；设置/取消提醒后刷新详情。
8. **未读角标**：登录后调用一次 `unread-count`，之后每 60 秒轮询一次（MVP 方案；P1 可换 WebSocket）。
